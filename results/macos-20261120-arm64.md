# macOS results, 2026-11-20, arm64

Run by an agent on a shared Mac test machine, following
[docs/macos-testing-plan.md](../docs/macos-testing-plan.md). Every DDEV and
Kiri command ran with `DOCKER_CONTEXT` set to a Kiri context and
`DDEV_XDG_CONFIG_HOME` set to a Kiri-only global config. The default docker
context (OrbStack) and its DDEV projects weren't touched.

## Summary

- **Released Kiri 0.2.2 with released DDEV v1.25.5:** works for one project at
  a time (18/18 smoke checks). A second project started while the first runs
  fails on problem 5 (Kiri won't disconnect the router from its first
  network). #594 is present in 0.2.2 but doesn't affect v1.25.5, which never
  copies the mkcert CA into the container. DDEV main after v1.25.5 does copy
  it, and that's what fails on Linux.
- **Released Kiri with the DDEV workaround branch** (794c0a4): works,
  including two projects at once (18/18 each, router recreated).
- **#595 on macOS:** the fix works. The repro gives `1234 1235 600` / `key` on
  the fixed build and `0 0 600` / `Permission denied` on 0.2.2.
  `cp-in-keeps-owner` passes on the fixed build and fails on 0.2.2. The e2e
  suite has no failure on the fixed build beyond one environmental check that
  also fails on 0.2.2.
- **macOS-specific checks that failed:** the Finder (NFS) mount hangs on every
  access, for both engines (both started with `kiri daemon` by hand, not from
  the app). Released DDEV can't start a project while Kiri's DDEV router is
  running unless the router's hostnames stay the same (problem 5, which also
  bites with only one project running). Kiri's own forwarded SSH agent socket
  isn't in DDEV's web container (DDEV's own agent works).
  Everything else passed: router ports on localhost, Xdebug through
  `host.docker.internal`, bind-mount ownership, Mutagen, idle VM sleep and
  wake, Kiri restart, Drupal 11, and amd64 images through Rosetta (see step 8).

The plan expected `FAIL ddev start`. It passes because v1.25.5 keeps the CA
in `/mnt/ddev-global-cache/mkcert` (a volume, files owned by the Mac uid 505)
and doesn't `docker cp` it into `/usr/local/lib/ddev/mkcert`. The Linux run's
"released DDEV" was v1.25.5-87 from main, which does. The first `ddev start`
took 221s mostly because of image pulls on a slow network.

Two projects with v1.25.5: `kirirel1` passed 18/18 (start 22s). `kirirel2`,
started while `kirirel1` ran:

```
FAIL ddev start
Failed to start kirirel2: failed to update router network aliases: failed to disconnect container 0fce48fc43ec… from network ddev_default: Error response from daemon: Kiri cannot disconnect a container from its first network (ddev_default)
```

That's problem 5. Kiri 0.2.2's message is shorter than the one in the Linux
notes, which came from a newer build (the fixed build here prints the long
form, see step 7).

## Step 6: details

- First e2e attempt on `kiri-ddev`: stalled in "container files in Finder"
  and was stopped at 30 minutes. `ls ~/"Kiri Ddev"` and `ls ~/Kiri` both hung.
  A `shasum` on a file under the mount (from `finder-hash`) stayed stuck in
  the kernel. Later the engine's own shutdown waited on `umount -f ~/Kiri Ddev`
  until that `shasum` was killed.
- Second attempt with `tests/e2e-nofinder.sh` (the Finder section wrapped in
  `if false`): totals above. Logs: `e2e-kiri-ddev.log`, `e2e-kiri.log`.
- The Finder mount still hung after a clean restart of the dev engine, so
  stale mounts from a daemon restart don't explain it.

## Step 7: fixed Kiri, released DDEV

`PERFORMANCE_MODE=none` `kirinone`: 18/18, start 230s (first start on a new
engine, with image pulls), restart 18s. Bind-mount ownership checks pass with
`none` (virtiofs, Mac uid 505).

`PERFORMANCE_MODE=mutagen` `kirimutagen` while `kirinone` ran:

```
FAIL ddev start
ddev-router already running, pushing new config...
Failed to start kirimutagen: failed to update router network aliases: failed to disconnect container b6183e71b921… from network ddev_default: Error response from daemon: Kiri cannot disconnect a running container from its first network (ddev_default); stop the container first
```

As expected. The plan then said `ddev stop kirinone` and retry, but the retry
failed the same way: the failed start left `kirimutagen`'s containers running.
After `ddev stop kirimutagen` (no projects running) it **still** failed,
because the router outlives stopped projects and the new project's hostnames
change its aliases. After a scoped `ddev poweroff` (removing Kiri's router)
`kirimutagen` passed 18/18 (start 23s, restart 22s). `ddev mutagen st`:
`Mutagen: ok: watching`. A file written on the Mac showed up in the container
(`edited-on-mac-2`).

So with released DDEV on Kiri, the router has to be removed before starting
any project other than the one it was created for.

## Step 8: macOS-specific checks (on `kiri-ddev`)

1. **Xdebug: pass.** `xdebug.client_host` is `host.docker.internal`, which
   resolves to `198.19.248.254 host.docker.internal host.kiri.internal`.
   With a listener on the Mac's 0.0.0.0:9003, `XDEBUG_SESSION=1 php -r 'echo 1;'`
   connected and sent the DBGp `<init … language="PHP" …>` packet. The
   connection arrives from `127.0.0.1` on the Mac. (A first try with
   `nc -l 9003` received nothing. That was my listener, not Kiri: a Python
   listener on 0.0.0.0 got the connection with the same Xdebug settings.)
2. **File speed:** `ddev composer create-project drupal/recommended-project:^11 --no-interaction`
   in a fresh `drupal11` project took **43 s with `none`** and **62 s with
   Mutagen** (including the sync). The cache was cold for the first and warm
   for the second, so Mutagen is the slower of the two here. No comparison
   with OrbStack was made (the other provider was left alone).
3. **Drupal 11:** **pass with both modes.** Start 25 s; `ddev composer require drush/drush`
   11 s / 15 s; `ddev drush si -y --account-pass=admin` 10 s / 9 s,
   `[success] Installation complete`. The front page returned `200` over
   http (:28080) and https (:28443), title `Welcome! | Drush Site-Install`.
4. **mysql:5.7 (amd64):** **pass, but it isn't a Rosetta test.** A project with
   `--database=mysql:5.7` started in 77 s (restart 25 s), running
   `5.7.42-0ubuntu0.18.04.1-log`. DDEV now ships an arm64 build of it
   (`@@version_compile_machine` `aarch64`, image arch `arm64`), so the plan's
   assumption was out of date. Rosetta itself works:
   `docker run --rm --platform linux/amd64 alpine uname -m` prints `x86_64`
   in about 1 s, and all seven `rosetta-*` checks in Kiri's e2e suite pass on
   the fixed build.
5. **Idle VM sleep: pass.** The engine logged
   `VM asleep: idle; the next request wakes it idle_s=60`. After 180 s idle,
   the first `curl` to the site returned 200 in 0.58 s, and `ddev exec true`
   took 3 s.
6. **SSH agent: DDEV's agent passes, Kiri's isn't used.** `ddev auth ssh -f`
   with a throwaway key, then `ddev exec ssh-add -l` listed it
   (`256 SHA256:ApTSL5… kiri-throwaway (ED25519)`). Kiri's forwarded socket
   `/run/host-services/ssh-auth.sock` doesn't exist in DDEV's web container.
   DDEV doesn't ask for it, so nothing breaks.
7. **Kiri restart: pass, with a caveat.** SIGTERM to the dev engine logged
   `engine shutting down signal=15`, but the engine kept serving until a
   process stuck on the Finder mount was killed. Its shutdown was waiting on
   `umount -f ~/Kiri Ddev`. After that it stopped all containers and
   `the VM stopped`. Started again, `docker ps` answered after 0.9 s. The
   project's containers were `Exited (143)` (no restart policy, as with
   Docker), and `ddev start` brought it back in 21 s, answering 200.
   Not tested: quitting and reopening the app itself.
8. **DDEV's own tests:** not run (time, and the tests' `ddev poweroff`).

Also seen in the dev engine's log, repeatedly:
`the VM's NAT network is still unreachable; published ports keep going over vsock to=192.168.65.3:… error=No route to host (os error 65)`.
That's macOS Local Network privacy refusing the engine's connections to the
VM's NAT address (the same thing that hits Apple's container runtime on these
machines). Kiri falls back to vsock, and published ports worked throughout.
On a Mac with someone at the desktop, macOS would ask whether to allow it.

## Plan deviations

- **Scratch path:** `~/tmp/<session>/kiri-test` instead of `~/kiri-test`
  (this machine's rule for agent scratch files). Same layout under it.
- **Released DDEV:** the v1.25.5 release tarball in `kiri-test/bin`, not
  `brew install ddev`, so the Mac's own DDEV wasn't changed.
- **Engines started by hand** (`kiri daemon`) instead of opening the apps, to
  avoid dialogs and an administrator password prompt with no one at the
  desktop. The `kiri` and `kiri-ddev` contexts were created by hand.
- **Kiri's routers moved:** OrbStack holds 80/443 on localhost, and Kiri 0.2.2
  binds `*:80`/`*:443` anyway. The released engine ran with
  `KIRI_HTTP_PORT=38080 KIRI_HTTPS_PORT=38443`.
- **Kernel and disk reused** from the 0.2.2 app instead of built.
- **e2e without the Finder section,** after the full suite stalled there.
- **Router removal between projects** in step 7 (scoped `ddev poweroff`),
  also between `kiribase`/`kiriwa*` runs and before each step-8 project.
- **Slow network:** a first baseline failed on a webserver image pull
  (`Peer disconnected`) and a Mutagen download timeout, before the network
  was switched. Times for first starts include pulls.

The plan has been updated for these (`docs/macos-testing-plan.md`), and new
facts are in `docs/lessons-learned.md`.
